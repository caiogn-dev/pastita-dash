# 2026-10-20 — Marketing: a base de clientes não vira "0 clientes" quando a busca cai

## Baseline

- `git fetch origin --prune` + `git checkout -B loop-base origin/main` + `npm ci`: ok.
- **Base do PR:** `origin/main` em `c8d6ba7`.
- `npx tsc --noEmit`: **limpo** (antes e depois).
- `npm test`: **469 suítes / 2963 testes** verdes antes; **471 / 2969** depois
  (+2 suítes, +6 casos desta fatia).
- `npm run lint`: **9 erros + 260 warnings PRÉ-EXISTENTES**, em arquivos NÃO tocados
  (`OrdersHeatMap.tsx`, `common/Button.tsx`, `common/Badge.tsx`, `sidebarColuna.test.tsx`,
  `pagamentoAMenorAoVivo.test.tsx` etc.). Os arquivos desta fatia ficam com **0 erro / 0 warning**.
- Gate anti-acúmulo: **0 PRs `bot/` abertos**; nenhum PR aberto/fechado (14 dias)
  cobre este defeito da base de clientes.

## Problema — o vazio enganoso nasce na camada de serviço

A base de clientes (`SubscribersPage`, aberta pelo botão **"Ver contatos"** do hub
de Marketing) carrega os contatos por `useState`/`useEffect` chamando
`marketingService.subscribers.list`. Na falha, o `catch` da página só disparava um
`toast` (que some em segundos) e deixava `subscribers` em `[]`, com `loading = false`.
A tela caía nos KPIs zerados — **"Total na base 0"**, **"Receita identificada R$ 0,00"** —
e no vazio confiante **"Nenhum cliente na base ainda"**, dizendo a uma loja que já
vendeu que ela não tem cliente nenhum.

Mas o engano era mais fundo: **`subscribersApi.list` NUNCA lançava a falha**. O
serviço tenta `customers/` e, se cair, o fallback `subscribers/`; quando os **dois**
caíam (rede/500), o `catch` interno fazia `return []`:

```ts
} catch {
  return [];   // ← falha total vira "lista vazia"
}
```

Ou seja, o `catch` da página era **código morto** para falha de rede: o serviço
devolvia `[]` e a página nem recebia o erro para poder avisar. O vazio enganoso
nascia na camada de serviço, antes de qualquer tela. É o mesmo "vazio/zeros
enganoso" já corrigido em Clientes (#199), Cardápio (#202), Sessões (#204),
Perfis de empresa (#215) e tantas outras — aqui pela raiz.

## O que mudou

**1. `src/services/marketingService.ts` (`subscribersApi.list`):** quando os dois
endpoints caem, **propaga** o erro em vez de devolver `[]`. Assim o chamador
distingue "vazio de verdade" de "vazio porque caiu". Os dois consumidores já
tratam exceção: `NewCampaignPage` tem `try/catch` → `toast` (`Promise.all` com
`emailTemplates.list`, que já lançava), e a `SubscribersPage` passa a ligar o erro
acionável.

**2. `src/pages/marketing/SubscribersPage.tsx`:** novo flag `erro`, ligado no
`catch` e desligado no início de cada carga. O `loadCustomers` virou `useCallback`
para o botão de retry reusá-lo. Na falha **sem dado em cache** (`erro &&
subscribers.length === 0`), a página mostra um `EmptyState` acionável
(`role="alert"`, "Não foi possível carregar a base de clientes" + botão **"Tentar
de novo"** que refaz a busca) no lugar dos KPIs zerados e do vazio enganoso. Com
dado em cache (falha só ao atualizar), a lista segue na tela e o `toast` avisa.

## Antes / depois

| Situação | Antes | Depois |
|---|---|---|
| `customers/` **e** `subscribers/` caem | serviço devolve `[]` (falha some) | serviço **lança** a falha |
| Base de clientes com a busca caída | "Total na base 0", "R$ 0,00", "Nenhum cliente na base ainda" | erro acionável com "Tentar de novo" |
| Base realmente vazia | "Nenhum cliente na base ainda" | **igual** (vazio legítimo preservado) |
| Falha ao atualizar com dado em cache | — | lista segue na tela + `toast` |

  principal; principal cai e fallback responde devolve o fallback; **os dois caem →

  antes** do fix (a tela mostrava o vazio confiante).

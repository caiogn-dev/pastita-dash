## Problema — o vazio enganoso nasce no `catch` que engole a falha

`IndicacoesCard` (`src/pages/loyalty/IndicacoesCard.tsx`, aba Indicações da Fidelidade)
carrega a lista por `useEffect` chamando `cashbackService.indicacoes(storeSlug)`. No
erro (rede/500), o `catch` descartava a falha **em silêncio**:

```ts
.catch(() => { /* aba secundária: falha aqui não derruba a página */ })
.finally(() => { if (vivo) setCarregando(false); });
```

Com isso `linhas` ficava em `[]` e `carregando` em `false`, e a tela caía no vazio
**CONFIANTE**:

> **Nenhuma indicação ainda** · A indicação é rastreada pelo link que o cliente
> pega na página da carteira dele…

Ou seja: a uma loja que **já tem divulgadores**, o painel afirmava que ninguém
indicou ninguém — quando foi a busca que caiu. É irônico porque o próprio
comentário do arquivo já alertava para isso ("um vazio mudo faria o dono achar que
o programa quebrou quando ele só não começou") — mas o caminho de falha produzia
exatamente esse engano. É o mesmo "vazio enganoso" já corrigido em Clientes (#199),
Cardápio (#202), Sessões (#204), Agendadas (#205) e a base de clientes (#217).

## O que mudou

`src/pages/loyalty/IndicacoesCard.tsx`:

1. Novo flag `erro`, ligado no `catch` e desligado no início de cada carga.
2. A busca virou um `useCallback` (`carregar`) para o retry reusá-la; o `useEffect`
   só a dispara (e devolve o cleanup `vivo = false` que ela já retornava).
3. Na falha **sem dado em cache** (`erro && !linhas.length`), a aba mostra o
   `FalhaAoCarregar` canônico (`role="alert"`, "Não foi possível carregar as
   indicações" + botão **"Tentar novamente"**) no lugar do vazio enganoso. O vazio
   legítimo (resposta vazia de verdade) segue mostrando "Nenhuma indicação ainda".

Sem mudança de rede, de rota, de contrato de API nem de chaveamento por loja (a
carga segue por `storeSlug`). Risco baixo.

### Follow-up (revisão do Codex, P1 — vazamento entre lojas)

A primeira versão guardava a busca com um `vivo` de fechamento devolvido por
`carregar`. Mas o retry chama `carregar` como **callback de evento**
(`onTentarDeNovo`) e **descarta** esse retorno: o cleanup de uma busca de retry
nunca rodava. O caminho do bug: a loja A falha → clico "Tentar novamente" (retry
em voo) → **troco para a loja B** antes de A responder → a resposta tardia de A
fazia `setLinhas(indicações da A)`, **exibindo as indicações de um tenant no
painel de outro**. Exatamente o "vazamento entre lojas" que o loop persegue.

Troquei o `vivo` pelo guarda monotônico `requisicaoRef` (mesmo padrão do
`CustomerSessionsPage`): cada `carregar` captura `++requisicaoRef.current` e só
aplica sucesso/erro/fim-de-loading se ainda for a busca mais recente. Como a
`carregar` da loja B já incrementa o ref antes de a resposta de A chegar, a
resposta obsoleta é descartada — venha ela do efeito ou do botão. Novo caso de
teste (o 4º), **vermelho antes** do follow-up (a lista virava "Divulgador da loja
A" sobre a B), verde depois.
